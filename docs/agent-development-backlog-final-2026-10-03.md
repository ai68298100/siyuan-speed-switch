## 1. 这份账本解决什么问题

目前仓库同时存在 ROADMAP、当期 dev-plan、第三面板专项、R4 UI 候选任务和历史 UX 清单。它们有大量交叉：部分事项已经在生产代码完成，部分事项是同一缺口的不同描述，部分事项依赖真实思源桌面或 Android，不能由浏览器原型代替。

本账本把这些内容收敛成一套可以交给 AI agent 执行的工作单元。每个工作单元都包含目标、现有任务映射、依赖、建议代码入口、验收条件和停止边界。执行时以本文件的顺序和依赖为准，现有 `T-xxxx` 记录作为证据和历史来源。

本轮基线：

- 产品定位是思源笔记中的统一入口、上下文切换和工作界面编排平台。
- 第一面板负责找到、预览、打开内容和执行动作。
- 第二面板负责查看、刷新和编排信息组件；组件商店是第二面板内部视图。
- 第三面板是片段实验室，负责安全地管理、编辑、预览和保存 CSS/JS 片段；片段商店是实验室内部视图。
- 悬浮球只是全局入口和高频动作，不是第四个产品表面。
- 片段保存真源是思源原生片段列表；AI 只能生成待审核草稿；JS 预览继续 blocked。
- R4 原型已经覆盖平台外壳、三面板、组件商店、片段商店、设置、悬浮球、移动端主题和 AI 审查状态。
- 当前正式任务最高编号为 `T-7072`。本文件使用 `AB-` 执行编号，避免在没有完成去重和立项前抢占正式 `T-xxxx` 编号。
- 本文件共 47 个 `AB-*` 归并单元，但它们不是 47 个可以立即写生产代码的任务；必须先看标题状态。已完成/吸收项只做回归，环境项只采证，决策项只产出 ADR/原型，阻塞项保持阻塞。

## 2. Agent 执行规则

### 2.1 开始任何任务前

1. 阅读本文件对应任务、`ROADMAP.md`、`BLOCKERS.md`、相关 `docs/adr/`、当前 `docs/dev-plan-*.md`。
2. 用 `rg` 搜索任务映射的 `T-xxxx`、函数名、设置 key 和测试，确认缺口仍然存在。
3. 如果现有 `T-xxxx` 已覆盖目标，只补它的缺失验收或证据，不新造重复任务。
4. 如果确实是新工作，在当前 dev-plan 中按协议分配下一个正式任务号，并在任务记录中回写 `AB-` 编号。
5. 先写实施计划和影响文件，再改代码；一次只推进一个依赖闭合的工作单元。

### 2.2 状态枚举与执行权限

每个 `AB-*` 卡片标题后的状态标签决定 Agent 能做什么。卡片正文中的“目标”在 `verify-only`、`environment-gate`、`absorbed`、`done` 和 `blocked` 状态下是验收基线，不是重新开发授权。

| 状态 | Agent 可以做什么 | 明确禁止 |
| --- | --- | --- |
| `build` | 直接实现卡片范围内的生产代码、测试和文档证据 | 扩大范围或顺手重做已完成模块 |
| `conditional-build` | 先完成源码/测试差距审计；确认缺口后只实现缺口 | 未审计就整体重写；把候选 UX 直接变成正式功能 |
| `verify-only` | 运行现有测试、补证据、修复可复现回归 | 以“规范更完整”为理由重做已交付能力 |
| `absorbed` | 将历史任务映射到已完成实现，保留回归检查 | 新增同名实现或重新分配正式任务号 |
| `done` | 只做必要的回归和证据更新 | 把完成项重新排进开发队列 |
| `decision-gated` | 输出 ADR、原型、风险和选项，等待决策 | 在决策前写生产接线或上传链路 |
| `environment-gate` | 采集真实桌面、Android、窄侧栏或外部服务证据 | 用 Chromium/模拟器结果宣称宿主通过 |
| `maintenance` | 根据真实反馈修复具体组件缺陷并更新证据 | 重新扫 58 个组件或以新增数量作为目标 |
| `blocked` | 记录阻塞原因、复现条件和跳过路径 | 写占位实现、绕过安全边界或伪造通过 |

只有 `build`、审计确认缺口后的 `conditional-build`、以及完成决策后的 `decision-gated` 才能进入生产代码修改。所有任务仍须遵守本文件的受保护文件边界。

### 2.3 每个任务的共同实现顺序

```text
现状搜索 → 纯模型/状态合同 → 生产接线 → 错误与取消 → 键盘/触控/读屏
→ 普通 Chromium 验证 → 需要时做真实宿主验证 → 更新 dev-plan/ADR/证据
```

### 2.4 每个任务的共同完成条件

- 生产行为、R4 原型语义、双语文案和状态反馈一致。
- ready、loading、stale、dirty、blocked、error 中适用的状态都有明确文字、动作和回退。
- 异步请求有代际或取消保护；旧结果不能覆盖新状态；销毁后不再操作 DOM。
- 修改门禁或契约测试时，按 `docs/gate-audit-checklist.md` 做正向和负向验证；只证明“现在仍通过”不算完成。
- 跑与风险匹配的 `tsc`、单元/契约、smoke、浏览器交互、构建和包体检查。
- 真实思源桌面、窄侧栏、Android、外部网络和 AI SSE 的证据单独记录，不能用浏览器夹具冒充。
- 更新任务状态、证据、下一步；不把“代码完成”写成“真实宿主完成”。

### 2.5 明确不进入本轮主线

- CRM、人脉管理、项目管理、第二个文件树或第二个原生搜索页。
- 云同步、插件自建服务端、自动上传社区片段、Gist token 写日志。
- 自动读取整库、隐式上传正文、自动修改文档、自动启用 AI 片段。
- 任意 JavaScript 运行预览；除非用户另行确认并完成独立 runner ADR、安全测试和真实宿主验证。
- AI 智能排序覆盖用户固定顺序、页签关系图、统计追踪和大而全常驻批量管理。
- 版本号、`CHANGELOG`、README 徽章/安装信息和 `PROGRESS` 不属于普通任务修改范围。

依赖图：

同一阶段的 `build` 任务可以并行，但 `verify-only`、`environment-gate` 和 `decision-gated` 是前置门，不应被当成生产功能批次。每个阶段建议 3～5 个相关任务形成一次本地提交；完成一个阶段后再推送。

当前允许进入生产实现的最短路径是：

1. 先执行 `AB-0001`～`AB-0004`，把状态、证据、保护文件和验收夹具锁定。
2. 对 `AB-1001`～`AB-1103`、`AB-1201`～`AB-1204`、`AB-1301`、`AB-1402`、`AB-1404` 做 `verify-only`，没有复现缺陷就关闭，不写重做代码。
3. 按依赖推进第三面板真实缺口：`AB-1304` → `AB-1305` 的 ADR → `AB-1306` → `AB-1307`；`AB-1305` 的编辑器实现必须等待 ADR 结论。
4. 并行处理组件商店的 `AB-1205`，把 `T-7034` 的生命周期条件作为其验收条款；`AB-1206` 只采集宿主证据。
5. 处理设置真实缺口 `AB-1401`，再进行 `AB-1501`～`AB-1504` 的宿主、主题和无障碍验收。
6. AI 先做 `AB-1601` 的上下文/隐私合同；`AB-1603`、`AB-1604` 先审计再决定是否开发，禁止默认开启自动排序和匿名统计。
7. 主线收口后才进入 `AB-1801`～`AB-1803`；`AB-1804` 永久保持 blocked，除非另有明确安全决策。

- **目标**：所有 AI 调用前显示上下文选择器，明确当前文档、选区、块、搜索结果、片段和外部数据范围。
- **映射**：ROADMAP Agent 专项、ADR 0083、R4 `UIR-075`、`UIR-081`。
- **验收**：默认不读整库、不上传未选择内容；拒绝、超时、取消和上下文过大都有回退；日志不含正文和凭据。

### AB-1602｜Agent 只读能力矩阵和受控写动作【任务类型：verify-only】

- **目标**：整理 `workspace-context`、只读搜索、打开文档、日记、任务状态等能力的宿主能力、权限、取消、卸载和移动端矩阵。
- **映射**：`src/agent-capabilities.js`、`src/agent-workspace-runtime.js`、ROADMAP Agent 专项。
- **验收**：旧宿主无报错；能力声明与实际可执行动作一致；写动作有确认和副作用声明；批量关闭、删除和跨文档写入继续默认关闭。

### AB-1603｜AI 建议解释和工作现场辅助【任务类型：conditional-build】

- **目标**：支持解释搜索结果、组件错误、片段作用域/冲突/副作用、工作现场名称和摘要。
- **映射**：R4 `UIR-077`、`UIR-078`、`UIR-082`。
- **验收**：建议显示依据和上下文范围；不会覆盖用户固定排序；工作现场应用前显示差异；用户拒绝后不重复强推。

### AB-1604｜诊断、性能和质量指标【任务类型：conditional-build】

- **目标**：建立首屏、首批搜索、局部刷新、预览、面板切换、焦点恢复、工作区恢复和 AI 确认覆盖率指标。
- **映射**：`T-6954`、`T-7036`、`T-7048`、R4 `UIR-084`～`UIR-088`。
- **范围边界**：先做本地、可脱敏、可复现的质量证据；匿名使用统计、常驻指标上报和自动排序属于延后决策，不得默认接入。
- **验收**：指标不记录正文和个人路径；每项有预算、夹具、失败阈值和回归说明；性能退化先修复主路径再扩展功能。

## 13. 阶段 8：发布、文档和合并前收口（P0）

### AB-1701｜跨页面主流程回归门禁【任务类型：verify-only】

- **目标**：覆盖入口→首焦点→查询→预览→执行→回执→返回，以及工作台刷新、片段保存、设置即时保存和浮球进入。
- **映射**：`T-7015`、R4 `UIR-084`、`UIR-085`。
- **验收**：桌面、侧栏、移动；空、加载、失败、取消、脏稿、旧响应和部分失败；修改门禁时完成负向验证。

### AB-1702｜截图、浏览器和真实宿主证据矩阵【任务类型：environment-gate】

- **目标**：让每个 R4 状态页面都有结构、交互、键盘、触控、读屏和错误证据。
- **映射**：`T-7005`、`T-7015`、`T-7036`、`T-6995`。
- **验收**：截图只证明视觉/结构；真实桌面/Android/内核/AI 网络证据独立列出；不把临时截图提交到源码目录。

### AB-1703｜源码、动态 chunk、包体和文档一致性【任务类型：verify-only】

- **目标**：核对源码入口、动态 chunk、组件目录、片段商店、安全边界、README 能力说明和发布包的一致性。
- **映射**：`T-7048`、`T-7021`。
- **验收**：不越过版本/CHANGELOG/README 徽章/PROGRESS 保护边界；功能清单不声称未验证的宿主能力；包体预算和动态 chunk 命名不回归。

### AB-1704｜合并前账本清理【任务类型：build】

- **目标**：把完成、部分、阻塞、取消、待用户决策的任务在 ROADMAP、dev-plan、ADR、第三面板计划和本账本中对齐。
- **映射**：`T-7047`、`T-6983`、`T-6984`、`T-6996`。
- **范围边界**：只更新任务账本、ROADMAP、dev-plan 和 ADR 之间的状态关系；版本号、`CHANGELOG`、README 徽章/安装信息、`PROGRESS` 仍受保护，不能由此任务修改。
- **验收**：没有孤儿任务、重复任务或把研究写成生产完成的条目；每个阻塞有跳过路径；下一批可直接从一个依赖闭合任务开始。

## 14. 阶段 9：可选生态扩展（P2，主线收口后再开）

### AB-1801｜片段商店本地目录和配置包【任务类型：decision-gated】

- **目标**：在实验室内部提供本地精选、我的片段、用途标签和配置包预览；加入草稿，不自动启用。
- **映射**：`T-6962`、`T-6963`、`T-6997`。
- **决策拆分**：先决定商店定位、渠道、元数据和来源信任（`T-6962`/ADR）；决策通过后才允许开发本地目录和配置包（`T-6963`）。
- **前置**：`AB-1301`～`AB-1306`、`AB-1701`。
- **验收**：来源、许可证、远程资源、影响范围和兼容端可见；导入逐组差异确认；远程内容按文本节点处理。

### AB-1802｜社区共享渠道决策【任务类型：decision-gated】

- **目标**：先决定仅本地投稿包、官方目录还是外部社区目录，再决定是否开发共享链路。
- **映射**：`T-6964`。
- **停止条件**：没有用户确认、渠道、隐私和安全决策时不写社区上传代码。

### AB-1803｜58 个组件滚动规格和专项优化【任务类型：maintenance】

- **目标**：按组件家族完善材质、档位、数据边界、空/错/缓存状态、三端收缩和商店预览。
- **映射**：`T-6965`、`T-6971`、`T-6997`。
- **前置**：`AB-1201`～`AB-1206`。
- **验收**：每批规格卡、生产接线、契约测试、负向验证和包体检查齐全；不以新增组件数量作为质量指标。

### AB-1804｜JS 方向复议【任务类型：blocked】

- **目标**：默认继续 blocked；只有用户明确要求受限模拟执行时，单独写 runner ADR、权限白名单、终止、时间/内存和日志方案。
- **映射**：`T-6996`。
- **停止条件**：用户没有明确选择或安全合同未通过时，保持 blocked，不做占位实现。

## 16. 推荐的第一批开发选择

如果没有新的用户决策，下一次 Agent 应按下面顺序选择；每一项都要先读取标题状态：

1. `AB-0001`～`AB-0004`：重算状态、登记重复项、检查受保护文件并固定验收夹具。
2. `AB-1001`～`AB-1103`、`AB-1201`～`AB-1204`、`AB-1301`、`AB-1402`、`AB-1404`：只做 `verify-only`；发现可复现回归才开最小修复。
3. `AB-1304`：补原生片段管理缺口和回收站闭环，保持思源原生列表为唯一真源。
4. `AB-1305`：编辑器 ADR 与包体/兼容性证据已完成；CodeMirror 6 暂缓，不引入远程依赖，轻量 textarea 路线已验证。
5. `AB-1205`：实现组件商店真实内联预览与取消/释放生命周期；不要重做已交付的 58 个组件规格。
6. `AB-1306` → `AB-1307` → `AB-1601`：先做目录元数据，再做 AI 状态/审核回执，最后接入上下文和隐私合同。
7. `AB-1401`、`AB-1501`～`AB-1504`：设置缺口完成后采集真实宿主、主题、移动和无障碍证据。

`AB-1104`、`AB-1105`、`AB-1302`、`AB-1303`、`AB-1401`、`AB-1603`、`AB-1604` 属于 `conditional-build`：必须在任务记录中附上现有实现搜索结果和复现差距，才可以把候选项转成正式 `T-xxxx`。选择原则是先修复“用户会丢失现场、误以为成功或无法恢复”的问题，再扩展商店、AI 和生态；任何主流程回归都优先修复，暂停叠加新功能。
