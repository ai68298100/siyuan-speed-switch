# R11 聚焦调研（2026-09-27）：多窗格/并排打开的宿主能力边界

> 轮次：R11（R10 后滚入）。主题直接决定两条线的去留：R2 池"并排打开"候补、工作区恢复 2.0 的布局维度能否升级为"窗格排布"。取证以本地 `node_modules/siyuan` 官方类型定义为准（公开插件 API 面）。

## 1. 取证结论

### 1.1 打开侧：并排打开是公开能力（且早已交付）

- `openTab` 官方签名含 **`position?: "right" | "bottom"`**——向右侧/下方分屏打开是类型化的公开选项。
- **R2 池销项**：速切早在 T-6810 就用它交付了"右键搜索结果 = 右侧分屏打开"（`openDocSearchResult(position)` → `document-actions` → openTab）。账面候补"并排打开"实为已交付未销项，本轮销项。
- **本轮补齐的缺口（T-6924）**：鼠标有右键、键盘链（Enter/Alt）没有分屏等价物。已补 Ctrl+点击/Ctrl+Enter = 右侧分屏（Alt 保持预览优先级；手机端不绑定）。

### 1.2 感知侧：窗格归属可类型化访问但语义未文档化

- `getAllTabs()/getActiveTab()` 返回的 `Tab` 公开暴露 `parent: Wnd`，`Wnd` 有 `resize?: TUILayoutDirection`、`children`、`parent?: Layout`——理论上可遍历内部布局图判定某文档在主区/右侧/下方案窗格。
- **判定：捕获侧 v2 不做**。`parent` 图的语义（根布局子序、方向组合）无文档承诺，跨版本脆弱；基于它做快照会把"布局维度"建立在私有结构上。维持 v1（活动文档维度），等上游把窗格查询文档化或用户真实反馈再加。

### 1.3 布局维度 v2 的可达上限（记录，不立项）

若上游开放窗格查询，文档集可升级为 `{rootId, pane}` 快照 + 恢复时按 `position` 回放，实现真正的"双栏工作区恢复"。当前公开 API 下最远只能做到"打开顺序 + 活动文档"（已交付）。

## 3. 防反复

- 不要再为"并排打开"立项——它已存在（右键 + Ctrl+点击/Ctrl+Enter）。
- 不要基于 `Tab.parent` 内部图做任何持久化语义。
