# T-6865 三大面板与统一切换平台再梳理（2026-09-25）

> 本轮只做功能、交互、UI 和产品定位研究，不修改生产代码。目标是把页签面板、组件面板和悬浮球放进同一个可解释的产品模型，找出真正需要补的能力，并明确不应继续扩张的边界。

## 1. 定位先改成什么

当前“页签与文档导航器”的表述已经不能完整覆盖现有能力；“主页”也不能准确描述组件面板。建议将产品定位升级为：

> **小驴雷切：思源笔记的统一切换与工作上下文平台。**
>
> 它把内容、功能、工作现场和信息组件放进一个本地优先的切换体系，让用户可以快速找到、预览、打开、恢复或执行下一步操作。

“各种各样切换的总平台”可以作为面向用户的通俗表达，但产品正式表述需要把“切换什么”说清楚：

| 切换对象 | 主要内容 | 主入口 | 用户意图 |
|---|---|---|---|
| 内容切换 | 已开页签、文档、收藏、最近关闭、搜索结果、关联内容 | 第一面板 | 找到并回到某个内容 |
| 功能切换 | 日记、搜索、设置、宿主命令、插件动作、快速捕获 | 命令模式、快捷动作、悬浮球 | 立即执行一个动作 |
| 现场切换 | 文档集、布局、筛选、场景、悬浮球动作集、皮肤 | 第一面板工作台、设置、悬浮球预设 | 恢复一套工作状态 |
| 信息切换 | 时钟、任务、天气、统计、数据库、第三方只读组件 | 第二面板 | 快速查看当前需要的信息 |

因此，三块 UI 的关系应固定为：

```text
                统一切换与工作上下文平台
                         │
        ┌────────────────┼────────────────┐
        │                │                │
   第一面板          第二面板          悬浮球
   内容导航面        信息工作台        全局触发器
   找到/预览/打开    查看/刷新/配置    呼出/执行/恢复
```

第一面板负责“去哪儿”，第二面板负责“看什么”，悬浮球负责“从哪里快速触发”。三者共享结果模型、动作 registry、工作区状态和能力说明；它们保留各自适合的布局和输入方式。

## 2. 当前仓库能力盘点

### 2.1 第一面板：页签与文档导航

当前实现已经超过单纯页签切换器：

- 已开页签本地即时过滤，随后接入已打开文档内容和全库结果；
- 统一索引包含页签、收藏、最近关闭、文档集、动作等来源，并做去重、来源标记和截断计数；
- 标题、路径、拼音、查询语法、笔记本、类型、排序和搜索方式已形成组合过滤；
- 页签卡支持当前项、分组、收藏、关闭、缩略图懒加载、数字直达、键盘方向导航；
- 已有搜索结果预览窗格，支持焦点/悬停触发、sticky 吸顶和窄屏降级；
- 空查询有工作台，包含收藏、最近、文档集、保存搜索、动作和关联内容等入口；
- 桌面、侧栏、移动端使用共享导航模型，端侧 UI 独立装配；
- 快捷动作底栏、右侧动作栏、命令模式和设置入口已经接入。

当前真正的缺口：

1. **对象与动作的语义还没有在 UI 上彻底分开。** 同一个搜索结果区可能同时出现“打开文档”和“执行命令”，来源标识存在，但用户还需要自己判断副作用和结果类型。
2. **空查询和输入查询的层级需要更稳定。** 空查询应优先固定和最近，输入后再进入搜索；工作台、结果区和异步状态不能互相挤占首屏。
3. **排序理由还不够可解释。** 目前有 exact、标题、路径、拼音、MRU 等能力，但没有统一的“为什么排在这里”与重置学习排序入口。
4. **页签卡的信息层级仍需收口。** 更新时间、未保存/有改动、当前分栏、来源和可执行动作需要形成稳定的主次关系；T-6848 已登记但尚未开工。
5. **行级动作不够完整。** 关闭、固定、收藏、复制深链接、在右侧打开、在侧栏定位等可以进入统一 Action Panel/长按菜单，减少右键和隐藏行为的差异。
6. **跨面板状态连续性还可加强。** 从组件、悬浮球或搜索结果进入第一面板后，应能恢复查询、筛选、选中项、预览和滚动位置，而不是每次回到默认空态。
7. **首帧与大列表需要继续实测。** 本地过滤和性能门禁已经有，首帧骨架仍应先用数据决定；T-6849 继续保持“先测后做”。

### 2.2 第二面板：组件与信息工作台

当前实现已经具备工作台和组件生态的主体：

- 桌面使用 12 列网格，移动端切为单列，组件有多种尺寸档位；
- 组件可添加、删除、排序、折叠、配置、调整尺寸，桌面支持拖动，移动端提供上下移动；
- 组件商店支持内置组件、第三方 provider、外部只读来源、来源/提供方分组、搜索、筛选、折叠、计数、排序、密度和 grid/list/compact 视图；
- 组件状态区分 loading、ready、empty、error、cached、stale，并提供单卡重试和刷新全部；
- 组件支持来源、隐私、网络集成、依赖、支持端和预览信息；
- 组件配置、布局、商店视图状态跨会话持久化，数据库组件已补有界表格投影；
- 组件协议以只读数据函数为核心，单组件失败不会拖垮整面板；
- 第二面板可从第一面板、快捷动作和悬浮球打开，并有 follow/adaptive/custom/fullscreen 尺寸模式。

仍需补足的地方：

1. **面板角色需要更明确。** “信息工作台”“组件管理器”“组件商店”目前都在同一条进入路径上，用户首次打开时不一定知道当前是在查看、编辑还是添加组件。
2. **组件与当前上下文连接不足。** 工作台主要是全局信息集合，缺少“当前文档/当前工作区/当前场景”的轻量过滤和上下文组件入口。
3. **编辑模式的反馈还可以更直观。** 需要清楚显示“正在编辑布局”、拖动落点、未保存布局变化、恢复默认、撤销上一步和移动端排序反馈；移动端不应依赖拖拽。
4. **刷新和健康状态需要就近呈现。** 全部刷新入口已有，但组件级更新时间、下次刷新、失败原因、缓存年龄、来源健康和暂停刷新原因应能从卡片直接看懂。
5. **商店与已安装区应有更清晰的入口分层。** “可用”“需安装提供方”“已添加”“推荐/新”需要用同一套状态语言表达，避免用户把目录条目误认为已经可用。
6. **组件间的布局和现场关系还不够强。** 文档集/场景切换时是否跟随组件布局、哪些组件属于某个工作现场、恢复失败如何逐项回执，需要进入后续工作区模型。
7. **时钟类组件的整卡重建仍是工程债。** ROADMAP 中 F1 已登记，应以局部文本更新和焦点/滚动稳定为目标；不通过全量虚拟化掩盖问题。

### 2.3 悬浮球：全局触发器

当前悬浮球已经从一个按钮发展为共享动作入口：

- 复用 quick-action registry 和统一 executor，当前目录约 34 个动作；
- 桌面和手机保留独立配置，侧栏已按 ADR 0072 撤出；
- 支持主点击动作、拖动分流、首层最多 6 项、更多面板、分组、搜索、启用开关和设置直达；
- 支持位置记忆、边缘吸附、自由停放、半隐藏、闲置降透明、滚动隐藏、弹层让位、全屏/后台隐藏和恢复把手；
- 支持宿主命令、插件命令、组件面板、快速捕获、日记、最近关闭、同步、模板等动作；
- 支持动作名称/图标覆盖、端侧能力状态、unknown/unsupported 原因和手机端显式尝试；
- Pointer Events、touch slop、命中几何、焦点恢复、Escape、键盘等效入口、执行超时和生命周期清理已有自动化验证。

仍需补足的地方：

1. **平台入口的主语义要稳定。** 默认轻触应始终能打开统一切换平台；自定义主点击可以保留，但不能让用户失去最基本的恢复入口。建议把“打开平台”作为不可删除的系统级回退，而不是普通可选动作。
2. **首层、更多、底栏和命令模式需要更明显的分工。** 首层只放每天高频动作，更多负责完整动作目录，底栏负责当前面板快捷入口，命令模式负责键盘和参数动作；同一动作在不同入口的标签、能力和结果应一致。
3. **固定、首层、收藏、场景绑定是四种不同关系。** 现在容易把“排序靠前”当作“固定”，后续应把 pinned、favorite、firstLayer、sceneBinding 分开建模和展示。
4. **动作结果需要更可解释。** 执行中的状态、参数输入、宿主不可用、权限不足、失败重试和成功后的回到原面板应有统一回执；动作行应显示副作用级别。
5. **手机宿主手势仍需真实验收。** `data-prevent-swipe`、滚动隐藏、离边停靠和上滑呼出都不能用 Chromium 模拟替代 Android 证据，B-004/B-005 继续有效。
6. **动作目录继续扩大前要先稳定分类。** 数字槽绑定、四向径向菜单和场景动作值得保留为候补，但必须建立动作类型、输入、能力、权限和恢复路径，否则“总平台”会变成一个难以浏览的按钮仓库。

## 3. 外部产品和参考插件的共同结论

思源参考插件提供了三个互补方向：

- [Quick Switch](https://github.com/asdfcyt/sy-quickswitch-release) 把已开页签、模糊文档搜索、文档内搜索、快速日记和键盘导航放进一个轻量入口，证明第一面板的核心仍然是“输入即切换”。
- [Panda Navigation](https://github.com/hqweay/siyuan-panda-navigation) 把浮动导航、分组、预设、端侧显示、宿主命令和插件命令放在一起，并提供配置分享；它说明悬浮球可以成为“动作编排入口”，但自定义脚本和 GPL 代码不能直接带入本项目。
- [思源主页](https://github.com/Glaube-TY/siyuan-homepage) 与本项目组件面板重叠在“信息聚合”方向；本项目应保持只读组件协议、布局和来源健康优势，避免再次建设一个泛化主页。
- [思源文档搜索](https://github.com/Misuzu2027/syplugin-document-search) 和 [反链面板](https://github.com/Misuzu2027/syplugin-backlink-panel) 提醒我们：搜索结果、定位、反链和当前文档上下文应能在同一个导航体系中互相跳转。

外部统一入口产品给出的模式更一致：

| 来源 | 关键机制 | 应吸收的原则 |
|---|---|---|
| [VS Code Command Palette / Quick Open](https://code.visualstudio.com/docs/editing/getting-started/userinterface) | 命令执行与对象打开有不同入口；Quick Open、Ctrl/Cmd+Tab 和命令面板各有明确语义；视图可重排 | 平台内要区分“找对象”和“执行动作”，共享索引但不要混淆主动作 |
| [PowerToys Command Palette](https://learn.microsoft.com/en-us/windows/powertoys/command-palette/overview) | Home 展示最近和固定项；紧凑搜索框按需展开；Dock 是常驻入口；扩展可提供列表、详情、表单和上下文菜单 | 空查询优先最近/固定，悬浮球是入口层，参数动作在搜索中内联完成 |
| [Obsidian Quick Switcher](https://obsidian.md/help/plugins/quick-switcher) / [Command Palette](https://obsidian.md/help/plugins/command-palette) / [Tabs](https://obsidian.md/help/tabs) | 空查询显示最近；命令可固定；页签、工作区和移动底栏有独立入口 | MRU、固定、命令、页签和移动入口要互相连接但不互相冒充 |
| [Raycast Search Bar](https://manual.raycast.com/search-bar) | Root Search、Compact Mode、Action Panel、收藏、别名、参数、frecency 和重置排序 | 搜索行必须有上下文动作；别名/固定/最近独立建模；排序学习可解释且可重置 |
| [Chrome Tab Search](https://support.google.com/chrome/answer/2391819) | 专门搜索已开页签，结果行可直接切换或关闭 | 第一面板保留“只看已开项”的快捷范围和行内关闭 |

共性不是把所有内容堆在一个大弹窗，而是让一个平台拥有统一的结果协议，同时让每种结果保持清晰的激活语义。

## 4. 建议补充的统一平台底座

### 4.1 统一对象协议

为内容、动作、现场和组件建立同一套可展示描述，但不把它们强行变成同一种对象：

```ts
type SwitchTargetKind = "content" | "command" | "workspace" | "widget";

interface SwitchTargetDescriptor {
  id: string;
  kind: SwitchTargetKind;
  title: string;
  subtitle?: string;
  source: string;
  aliases?: string[];
  capabilities: string[];
  sideEffect: "none" | "navigation" | "localWrite" | "external";
  surfaces: Array<"desktop" | "mobile" | "floating">;
  ranking?: {exact?: number; prefix?: number; recent?: number; frequency?: number};
}
```

展示层只消费有界描述；执行层继续从现有 registry、host adapter 和组件 runtime 获取实际 handler。这样可以统一搜索、悬浮球、底栏、命令模式和组件商店的标签与能力状态，同时避免把展示注册表变成第二套执行器。

### 4.2 三态入口模型

- **空查询**：固定项、最近项、当前工作现场和少量高频动作；不请求全库。
- **普通查询**：内容、组件、现场和动作分区结果；先本地，再按需请求宿主。
- **前缀查询**：`@` 只看已开内容，`>` 只看动作，`#` 只看收藏/标签，`+` 进入现场/组件；前缀只是过滤视图，不建立第二套搜索引擎。

每个结果统一支持 Enter 主动作、Ctrl/Cmd+Enter 次动作、Action Panel/长按上下文动作；异步 provider 必须有取消、旧结果作废、加载副标题和来源/失败状态。

### 4.3 统一工作现场

把文档集、场景预设、组件布局和悬浮球动作集逐步纳入一个版本化的 `WorkspaceContext`：

- 内容：页签、收藏、最近、当前文档、可稳定获取的分栏信息；
- 筛选：当前查询、范围和结果类型；
- 信息：组件实例、尺寸、折叠和配置引用；
- 入口：悬浮球首层、底栏快捷动作、命令别名；
- 恢复：逐项成功、跳过、失败和重试。

第一阶段只组合已有稳定字段，不伪造宿主无法读取的编辑器内部状态，不另建云同步服务。

## 5. 按优先级的增量建议

### P0：先统一语义和可靠入口

1. 将产品名称/说明统一为“统一切换与工作上下文平台”，在第一面板、第二面板、悬浮球的标题、空态和设置说明中使用同一组词。
2. 把第一面板结果显式分成“内容”“动作”“现场”“组件”四类，空查询优先最近/固定；保留 `>` 命令模式并补 `@` 已开内容过滤。
3. 固定悬浮球轻触的统一平台回退入口；自定义动作仍可配置，但失效时必须回到平台入口。
4. 给三块入口补统一的 provider/能力/失败状态：来源、端侧支持、权限、网络、缓存年龄和恢复动作使用同一套标签。
5. 完成真实桌面、最窄侧栏相关面和 Android 的验收矩阵；自动化和 Chromium 结果继续标明范围。

### P1：改善每天的切换和恢复

1. 第一面板：页签更新时间/改动徽标、行级 Action Panel、固定/收藏/最近的独立语义、排序理由和重置学习排序。
2. 第一面板：保存当前搜索/筛选为命令，允许绑定悬浮球或数字槽；从组件和悬浮球返回时恢复搜索会话。
3. 第二面板：查看态与编辑态分层，补布局草稿、撤销一次、恢复默认、拖动落点和移动端排序回执。
4. 第二面板：组件卡显示更新时间、缓存年龄、来源健康和下一次刷新；商店统一展示已添加、可用、需安装和不可用。
5. 悬浮球：将首层、更多、底栏、命令模式和场景预设按职责分开；动作行补输入、权限、副作用、失败和重试信息。
6. 建立统一上下文切换：工作现场同时保存文档集、组件布局、筛选和入口配置的版本化投影，恢复有预览和逐项回执。

### P2：再扩展平台能力

1. 组件按当前文档、工作区和场景提供上下文视图，仍保持只读、有界和来源透明。
2. 移动端提供一个明确主入口（底部切换器或下拉 Quick Action），悬浮球与宿主侧滑、键盘和 safe-area 共同验收。
3. 组件商店补推荐、新增、依赖安装指引和本地导入导出；远程目录和社区发布后置。
4. 受控参数动作、深链接、剪贴板入口和第三方 provider SDK 逐步开放；每个动作继续声明能力、权限和副作用。

## 6. 明确不做

- 不把第一面板变成完整文件树、完整全文搜索或常驻复杂筛选台；
- 不把第二面板变成无限扩张的主页、广告目录或任意 iframe/HTML 容器；
- 不把悬浮球做成系统级跨应用覆盖层、自动点击器或无条件置顶工具；
- 不把固定、收藏、最近、首层和场景绑定混成一个排序字段；
- 不直接移植 GPL 项目实现、第三方脚本执行器或未经审核的网络动作；
- 不用浏览器模拟、桌面响应式或推测结果代替真实 Android/SiYuan 宿主证据；
- 不为了“总平台”重复建立第二套搜索、动作、组件执行架构。

## 7. 建议顺序

`统一定位与术语` → `统一结果描述/能力状态` → `第一面板对象/动作分区` → `悬浮球平台回退入口` → `页签信息层级和 Action Panel` → `组件健康/编辑态回执` → `WorkspaceContext 恢复` → `参数动作与生态协议`。

这个顺序先解决用户是否知道“自己在切换什么”，再解决切换是否快、是否能恢复，最后才扩展更多 provider 和场景。
